Building, shipping, running

Operations: how we know it works.

Three green unit suites prove three components work in isolation and say very little about the seam between them. Everything on this page exists because of that sentence — the verification matrix, the golden vectors, the upgrade gates, and the rule that a failure you cannot reproduce on demand will be discovered by users with money on the table.

The verification matrix

Clients and consumer boundaries

One core, five front ends, all driving the same session logic — and the boundary each one crosses is different, which is why the boundary tests matter more than the client tests.

  • CLI (app/main.cpp) — a thin REPL over bitpoker_client; the development reference.
  • Qt desktop — five screens with an animated felt table for TH and ZJH.
  • Android — Qt/QML mobile build.
  • TUI (bitpoker-tui) — terminal wallet + table with an intent watcher that auto-joins matched sessions; the usual host for unattended play.
  • Browser — the WASM path: gamecore.wasm via embind with JavaScript driving the session, behind the shared headless layer @bitpoker/poker-session (relay transport, gamecore worker, hand state machine, recovery judgement, fee discovery). The browser path never links the asio transport or the wallet layer — each front end injects its own signing stack.

Two further components share the same core: a dispatcher that routes intents to worker clients, and a robot player — a personality-driven bot for TH and ZJH built on a sans-IO DecisionView seam so the brain is testable without a network.

The WASM staging trap

The gamecore.wasm the browsers load is a committed binary. If you change gamecore source and forget to rebuild and commit it, nothing fails to build. The browser plays by the old rules, the native client by the new ones; opening stacks match so the first hand agrees, and the second hand forks — one side session aborted mid-play, the other stuck at showdown, escrow still locked on chain.

The gate: make wasm-stage (compile + copy + stamp source hash + sync the keplr-vendored copy) and make wasm-check, a pre-build gate on make webapp / make extension. tools/sync-poker-session.sh --check keeps the vendored copy from drifting.

Coordinated upgrades

pokerchaind and poker-relayd ship in one signed manifest but never switch at the same time: the upgrader only pre-stages chain binaries via cosmovisor add-upgrade, Cosmovisor cuts the chain at the governance-selected height, and the relay switches only after locally-synced nodes report the plan applied. Without that order, a new relay protocol runs against an old chain.

Four invariants, each corresponding to a network-wide failure:

  • A signed release must be a cgo adjudicator build. A pure build returns ErrAdjudicationUnavailable for every adjudication; auto-pushing one to all validators locks every disputed escrow forever. Three guards enforce it (no Makefile target produces a pure node; a hand-built pure binary refuses to start; the packager reads go version -m tags and the ArchiveHash stamp).
  • The chain plan in the manifest must have a registered handler in app/upgrades (plus declared StoreUpgrades for store add/remove). A missing registration is a network-wide halt at the planned height; the host re-verifies live with pokerchaind upgrades list --json before staging.
  • Relay versions must be comparable semver, all derived from one place (tools/version.sh): 0.4.0 on a tag, 0.4.0-dev.N after. Build numbers go only in the prerelease field — a four-segment 0.4.0.25 is not semver and gets rejected, and 0.4.0+25 is legal but, per spec, never compares, so the upgrade never fires and never errors.
  • The relay protocol number is raised in two releases. First ship a relay that serves N+1 while still accepting N, plus new clients; only once clients have actually spread does a second release raise relay.MinProtocolVersion. Raising the minimum is the one action that cuts old clients off.

Draining is not "refuse everything" — it is "accept no new sessions": in-progress sessions can still reconnect (refusing a reconnect locks two players and their escrow out forever, and the drain never finishes). Chain state flips to DRAINING so matchmaking stops assigning, /admin/resume is the only exit that doesn't kill live sessions, and the fleet staggers deterministically by hash(relay_id) inside the window — otherwise every relay drains in the same timer tick.

Swapping a binary is not an upgrade. Module state migrations only run at a governance-planned, registered handler's height. An in-place binary swap gives you new code reading old state with no symptoms — derived indexes self-heal lazily, params do not. After upgrading, check /cosmos/upgrade/v1beta1/module_versions; the version string alone will not show it.

Packaging

make deb produces seven packages (node / relay / upgrader / faucet / cli carry binaries by architecture; common and node-config are arch: all). Packages install software, not state: genesis, validator keys, relay node keys, keyrings and tomls are never touched (not even on purge), and nothing starts after install — a node without a genesis restart-storms, and an auto-register relay starts by locking a bond; neither is the package manager's call.

The dependency rule that matters: pokerchaind is not pure Go (cgo carries the C++ adjudication engine), and the library requirement cannot be written as Depends — library package names carry sonames that differ per distro, so the package would fail to install on a host that can run it. Only the three names that are identical on every Debian/Ubuntu (libc6, libstdc++6, libgcc-s1) stay in Depends; the rest go to Recommends, and the real requirement is checked by the postinst with ldd against the binary, naming the missing soname and failing the install.
