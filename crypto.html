Mental poker on FourQ.

Every card in play is an elliptic-curve ciphertext that neither player can open alone. This page is the crypto: how a card is represented, how two people shuffle a deck neither can see, how a single card gets revealed without revealing the rest, and how every protocol message signs itself into evidence.

Cards and joint keys

Each of the 52 cards is a point on the FourQ curve. A stack is an ordered vector of ElGamal-style ciphertext pairs under a combined public key formed by adding the two players' session public key points:

the whole trick, in one line P_comb = P_A + P_B (point addition on FourQ) card_i = Enc(P_comb, card_point_i) — neither sk_A nor sk_B alone decrypts sk_A + sk_B together → the card point → face value via the stack-zero table

This is the Barnett–Smart mental-poker construction. The property the whole system leans on is that the combined key is a sum: it is symmetric in the two players, so neither is a "server" and neither is privileged. Both key shares are needed to open anything, and each share is released only for the specific card the protocol says may be seen.

Session identity is not chain identity

A player's in-game identity is a FiatShamirSecretKey — a FourQ scalar plus its derived 96-byte public commitment (publicKey ‖ commitment ‖ random). This is a per-session game key, entirely separate from the chain account key.

The separation is what makes the dispute path survivable. Revealing the session secret key after a hand exposes that hand's cards — which are being adjudicated anyway — and nothing else. Funds are never at risk from a reveal, because funds are controlled by the chain key and the reveal is of a different key entirely.

The 96-byte public key is committed on chain in the player's GameIntent before any cards exist. That is what makes the later revelation checkable: the adjudication engine verifies session_secret_key · G == the on-chain public key point before it believes anything a disputing party submits. A player cannot reveal "a" key that happens to decrypt to favourable cards; it must reveal the key they committed to.

The shuffle

Shuffling happens exactly twice per hand, once by each player, in sequence:

  1. Player A shuffles Takes the canonical initial stack S₀, applies a secret permutation π and re-encrypts every card with fresh randomness rₓ under the combined key, producing stack S₁ plus a NIZK proof P₁.
  2. Player B verifies, then shuffles Verifies P₁ against (S₀ → S₁), then applies its own π′ and rₓ′, producing S₂ and P₂. S₂ is the deck the hand is played from.

The proof (NeffVerifibleMixing::ProveStack / VerifyStack) establishes that the output stack is a permutation-and-re-encryption of the input stack without revealing which permutation.

Order-independence is load-bearing, not incidental. Because the combined key is the sum of the two public key points, it does not matter who shuffles first, and verification does not depend on shuffle order. The adjudication engine relies on exactly this property when it reconstructs the shuffle chain from evidence that may be partial — it can verify the steps it has without needing to know which player's turn it was supposed to be.

The security argument, stated small

Two claims, both reductions:

  • For the deck to be biased, a player would have to produce a shuffle that is not a permutation-and-re-encryption and still pass the NIZK.
  • For a card to be read early, an adversary would need both key shares — and the protocol releases only one, for only the card being legitimately shown.

Note what is not claimed: that a player cannot learn something from the ciphertexts they themselves produced. They know their own permutation. What they cannot do is undo the other player's, and that is the whole requirement.

Revealing a card

To let the opponent see card i, a player emits a FiatShamirCardkey — a per-card decryption share with an attached proof that the share was correctly derived from the player's committed public key and that specific ciphertext.

  1. Validate before applying The receiver validates the share against the sender's public key before using it. An invalid share is a hard cryptographic fault, not a retry — see revealMyOpenCards, where a failed cardkey.validate() fails the hand.
  2. Combine and map Combining one's own share with the peer's yields the plaintext card point, which maps back to a face value via the canonical stack-zero table.

Message authentication: the history is the evidence

Every protocol message (MsgMove) carries a MsgHeader with a session id, a message id, the previous message id, type flags, and a SchnorrQ signature over the whole serialised message with the signature field zeroed. Signing uses the session key, not the chain key. Two properties follow, and the dispute system is built on both:

  • The message history is a signed, hash-linked chain. Neither party can later present a rewritten history: the adjudicator attributes every action to whichever seat's session key signed it, and uses that attribution — not the submitter's claims — to enforce turn order.
  • Evidence is self-authenticating. A player submits the opponent's own signed messages as evidence; the opponent cannot repudiate them.
message id structure — cheap ordering, duplicate detection and hand-boundary checks with no extra state message_id = (hand_id << 16) | round_id

The RNG problem

One subtlety with large consequences. The normal decryption helper path draws randomness internally. The adjudication engine must never draw randomness — any non-reproducible output inside consensus is a fork, not a bug — so it decrypts by a mathematically equivalent but RNG-free route: direct elliptic-curve point subtraction using the two known session secret keys. Same result, zero entropy consumed.

This is not a micro-optimisation. It is the reason the same verification code can run in a live client (where randomness is fine and expected) and inside a validator (where it is fatal), and it is enforced at runtime rather than by convention — see the three-layer determinism guard.

Why these choices

FourQ, not a standard curve Mental poker is point-multiply-heavy: 52 cards × 2 shuffles × re-encryption, plus NIZK verification, all in the interactive path where latency is felt. FourQ is chosen for speed at that specific workload. The cost is that every determinism question has to be re-answered per architecture, because it is not a library everyone has built for arm64 consensus before.
Barnett–Smart, not MPC General secure multi-party computation would give the same property with a stronger guarantee and roughly two orders of magnitude more work per card. The two-party structure of heads-up poker makes the ElGamal-sum construction sufficient, and it is auditable by a person rather than by a proof assistant.
Neff-style NIZK A shuffle without a proof is a player choosing the deck. Neff's construction gives permutation-and-re-encryption proofs that verify fast and, critically here, verify order-independently — which the partial-evidence reconstruction in the adjudicator needs.
SchnorrQ over the session key Signing every message with the chain key would put the player's wallet in the hot path of a latency-sensitive protocol and make every message a broadcast-candidate. The session key gives the same non-repudiation for evidence purposes and stays off the wallet.
