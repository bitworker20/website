Poker with no dealer,
no operator, no referee.

Two players shuffle the deck between themselves using mental cryptography — no server ever holds it. The stake is escrowed by a Cosmos SDK chain. If the players disagree, a deterministic C++ engine replays the hand inside consensus, from their own signed messages, and every validator reaches the same verdict.

How a hand works

Four planes, four different trust assumptions

Nothing about the game itself goes on chain. The chain holds money and, only when cooperation fails, judgment.

  1. 01

    Match and escrow

    A player publishes an intent — game, stake, terms. The chain matches two of them heads-up, escrows both stakes, and assigns a relay.

  2. 02

    Shuffle, jointly

    Each side permutes and re-encrypts the deck under a joint key and proves it did so with a Neff-style verifiable-shuffle NIZK. A card opens only when both key shares are released.

  3. 03

    Play through a relay

    Two consumer endpoints behind NAT cannot reach each other, so frames go through a relay that forwards ciphertext and learns nothing. Every message is SchnorrQ-signed and replayable.

  4. 04

    Settle — or be judged

    Both sign the same outcome and escrow is released to the final stacks. If one refuses or vanishes, the other files evidence and consensus adjudicates it.

What is actually hard

Six decisions the design rests on

Mental poker, not a shuffling server

The deck is a Barnett–Smart construction over the FourQ curve. Each shuffle carries a proof that it is a genuine permutation and re-encryption of the deck it received — so neither side can stack it, and no third party has to be trusted not to look.

Determinism as a link-time property

The adjudicator links bitpoker_gamecore only — never the asio transport or the wallet. A CMake boundary check enforces it, so a future #include cannot smuggle non-determinism into consensus: the link simply fails.

A three-layer determinism guard

Above that boundary sit fixed-width arithmetic and ordered containers, a frozen eight-case corpus replayed on x86_64 and arm64, and digests diffed against goldens in CI. Validators on different architectures must agree byte for byte.

Relays paid by their own adversaries

A relay collects a reward only by presenting bilateral receipts — one signature from each of the two mutually hostile players. The rake comes out of the pot, never from block subsidy, so the network does not depend on inflation to stay reachable.

Relay locations are never published

No endpoint appears on chain. A relay learns from consensus that it has been assigned a session and answers with an ECIES-sealed blob carrying a per-player one-time connect token. Nothing in the registry tells an attacker where to aim.

Failure modes designed first

A relayed connection gives no signal when the peer dies; a dispute path that never opens is not a dispute path. Silence detection, bounded waits, resume-after-reconnect and reproducible fault injection are part of the protocol, not afterthoughts.

Clients

One core, five front ends

Desktop, Android, terminal, CLI and a browser extension all drive the same session logic. The extension reaches it through WebAssembly; the validators reach it through cgo.

  • Qt desktop — five screens, animated felt table for Hold'em and Zhajinhua.
  • Android — the same Qt/QML build, packaged for phones.
  • Browser extension — a Keplr fork; gamecore.wasm with JavaScript driving the session and an intent-approval popup.
  • TUI — terminal wallet and table, with an intent watcher that auto-joins matched sessions; the usual host for unattended play.
  • CLI — a thin REPL over the client library; the development reference.
  • Robot player — a personality-driven bot for both games, built on a sans-IO decision seam so the brain is testable without a network.
