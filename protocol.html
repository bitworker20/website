The protocol: coroutines in, verdicts out.

A hand of poker, expressed as a C++20 coroutine pipeline over Boost.Asio, with the rules themselves kept in pure sans-IO functions so that the referee and the table run literally the same code. This page is the session layer: lifecycle, state machines, the shared community-card core, and the transcript both players sign.

Hand lifecycle

The base framework (P2PPokerGameBase / P2PPokerHandBase) drives every game type through the same coroutine pipeline, so asynchronous network code reads like straight-line logic:

p2p_poker_base — the whole skeleton runGame └─ per hand: runHand ├─ exchangeShuffleStack (two shuffles + two NIZK verifications) ├─ runGameLogic ← game-specific; the only virtual step └─ settleHand (signed settlement transcript)

Concrete games implement runGameLogic() and getWinAmount(). The game loop checks getContinueHand() after each hand and calls settleGame() when the session ends. Everything above the virtual step is shared, tested once, and identical across games — which matters because the adjudicator walks the same shape.

A game the adjudication engine cannot replay has no business escrowing money. The chain validates game_type at intent time against the list of games the engine understands (TH, ZJH, O8 — one list, in pokerchain/x/pokerchain/types/game_type.go) rather than discovering it at dispute time. When the CC toy game was deleted, the reason was exactly this: the engine fell back to TH for unknown types, so a CC dispute would have been silently adjudicated as Texas Hold'em.

Sans-IO state machines

For every game the rules live in pure functions with no I/O and no network concepts:

heads-up hold'em, as the engine sees it HeadsUpHoldemState create_heads_up_holdem_hand(...); HeadsUpHoldemActionResult apply_heads_up_holdem_action(HeadsUpHoldemState&, action); bool heads_up_holdem_hand_complete(const HeadsUpHoldemState&); void settle_heads_up_holdem_showdown(HeadsUpHoldemState&, int cmp);

This is not merely tidy. The adjudication engine replays disputes through the exact same functions the live game uses. There is deliberately no second implementation of "the rules, as understood by the referee" — the classic source of arbitration systems that disagree with the game they arbitrate. When the engine rules an action illegal, it is illegal by the same code that would have rejected it at the table.

The practical rule when changing rules code: every change to apply_heads_up_holdem_action or its equivalents is a consensus-relevant change. It changes what verdict the engine reaches for old evidence, so it requires an engine version bump and a coordinated chain upgrade — not just a client release.

The community-card core

Texas Hold'em and Omaha are the same code with two configurations (ADR-011). Hand orchestration (community/community_hand_core.cpp), the asio driver (community/community_game.cpp), action codec (community/community_protocol.cpp) and the adjudication pipeline (adjudicateCommunityPrepared) are all shared. A game contributes exactly one CommunityRules:

hole card count2 for TH, 4 for O8 — drives the seat layout, nothing else.
three wire tagshole / board / showdown message tags per game.
showdown resolverthe ranking function: 7-choose-5 for TH, exactly-2-from-hole + 3-from-board (plus hi/lo split for O8).

The card-slot layout is defined in exactly one place — first [0, n) / second [n, 2n) / board [2n, 2n+5) — and live play, the wire codec and on-chain adjudication all index from that same source. The adjudicator therefore cannot index a card differently from the game. Adding the next community-card game means filling in those three hooks.

GameKind has three values and adding a fourth produces no compile error. The codebase used to be full of kind == TexasHoldem ? "TH" : "ZJH", which would draw Omaha as Zhajinhua — three hole cards, no board area. New code must go through include/common/decision_view.hpp's game_kind_code() / is_community_card_game(), or be an exhaustive switch.

The three games

TH — heads-up Texas Hold'em The primary game: preflop / flop / turn / river / showdown, check, call, bet, raise, fold and all-in, blinds derived from the effective stake, and a 7-choose-5 evaluator covering all ten hand ranks including the wheel straight and royal flush.
O8 — Omaha Hi-Lo Four hole cards, exactly 2 from hole + 3 from board, 8-or-better low hands split the pot. Betting is no-limit, not pot-limit: adding a pot-limit cap inside apply_heads_up_holdem_action would make Texas's every-hand consensus path depend on code Texas never executes (ADR-011 §2.3).
ZJH — Zhajinhua Three cards per player, blind-or-look betting, comparison-based showdown. The codec lives in *_state rather than a separate *_protocol file.

The settlement transcript

At the end of a hand the two clients exchange a MsgSettle carrying both seats' amounts, both continue-flags, and both signatures. The transcript that gets signed (SettlementTranscriptContext) binds:

  • a domain string and schema version;
  • the chain session id and the final stake;
  • both addresses and the winner / split outcome;
  • the hash of the final settle message; and
  • critically, the relay fee raked on chain together with the net per-seat amounts after that rake.

That last binding is a lesson learned, not an obvious design. If players sign the pre-rake game distribution, they are signing something the chain will not actually pay, and any later reconciliation is ambiguous. The transcript signs the true on-chain payout. When you extend the transcript, extend it to match what the keeper will actually move — never what the game "would have" paid.

Reconnection and resynchronisation

Frames carry a per-sender sequence number reused from the relay frame header's request_id. On reconnect:

  1. Client sends SessionResume with the highest sequence it received.
  2. Peer retransmits everything newer and replies with its own high-water mark, so the exchange is symmetric.
  3. Receivers deduplicate by sequence so overlapping retransmission is harmless. A MSGTYPE_RESYNC mid-hand resynchronisation lets an interrupted hand continue rather than escalate.

The relay contributes two behaviours discovered to be necessary the hard way: a reconnecting client with the same player id displaces the half-open old connection (otherwise the ghost holds the slot), and an overflowing outbound queue disconnects the slow consumer rather than silently dropping frames — a silently dropped frame desynchronises the protocol in a way that looks exactly like cheating.
