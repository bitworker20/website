Plane 3 · the money

pokerchain: escrow with no dead ends.

A Cosmos SDK application chain whose base denomination is uchip (exponent 0, display CHIP at 10⁶). It matches players, locks their stakes, assigns relays, releases money on cooperation, and — only when cooperation fails — becomes the court of last resort. This page is its state machine and the invariant that keeps every wallet whole.

Intents and matching

MsgOpenGameIntent carries:

game_typeTH / O8 / ZJH — validated against the engine's capability list, not free text.
stakeEscrowed into the pot immediately on acceptance.
opponent (optional)A named opponent for a private match; otherwise open matchmaking.
session pubkey (96 B)The in-game FiatShamir public commitment — what a later secret reveal is checked against.
transport pubkey (33 B)Compressed secp256k1, used only for the ECIES endpoint blob the relay delivers.

Compatible pending intents are matched in-consensus. Matching creates a GameSession, assigns relays (see assignment–answer), snapshots the relay fee, and pseudo-randomly assigns seats by session hash — so neither player chooses the button.

Session lifecycle

GAME_SESSION_STATUS_* — five states, every one with a bounded exit matched both results agree (intent) ──────────────► ACTIVE ─────────────────────────────► SETTLED │ one result submitted ▲ ├──────────────► RESULT_PENDING ────────┤ │ │ result timeout │ │ evidence ▼ │ ├──────────────► DISPUTED ─────────────┘ │ adjudicate / deadline refund no relay answer / active timeout └──────────────► CANCELLED (escrow refunded)

The transitions that matter during development:

  • ACTIVE → SETTLED is the happy path: both seats submit matching SubmitSessionResults.
  • ACTIVE → RESULT_PENDING when one result is in and the peer's matching result is awaited; a matching second result settles, a timeout escalates.
  • → DISPUTED on the first SubmitSessionEvidence. Escrow is protected and the dispute deadline is stamped.
  • → CANCELLED for sessions that never got service or never played: voided assignments and active timeouts refund both stakes.

The liveness invariant

Every state that can hold escrow must have an exit that a non-player can take after a bounded height. This is an invariant, not a collection of individual handlers. escrow_liveness_test.go walks the state enum to enforce it: add a new state without adding its exit test and the suite fails.

Concretely, the three exits are:

ACTIVEvoidAbandonedSession after session_active_timeout_blocks — someone may void a session nobody is playing.
RESULT_PENDINGAfter active_deadline_height, anyone may escalate to DISPUTED.
DISPUTEDPermissionless adjudication after the dispute deadline; failing that, a no-engine refund after dispute_refund_height.

The general lesson, from the incident that created this rule: in an escrow system the state diagram must be read as a liveness diagram. A state with no outgoing timed edge is a fund-loss bug even when no code path is wrong.

Cooperative settlement

The happy path is SubmitSessionResult from both seats. When the two submissions agree, settlePot releases escrow — paying each seat its final chip stack, with the relay rake deducted — and the session becomes SETTLED.

Conservation (payA + payB + fees == pot) is asserted inside the keeper, and a bank-transfer failure rolls back the entire settlement rather than recording a verdict whose money never moved. The same conservation law holds on the dispute path: player_a_amount + player_b_amount == 2 × stake, with the dispute fee taken from the at-fault side's share, never added to the pot.

Escalation: three messages, order matters

When cooperation fails, a dispute is three on-chain messages and they cannot be reordered:

  1. MsgSubmitSessionEvidence Pins the signed message history on chain. The session turns DISPUTED, escrow is protected, and dispute_deadline_height is stamped.
  2. MsgSubmitSessionSecret Reveals the hand's session scalar (not the chain key). The chain only accepts it after DISPUTED, so nobody can leak a live game early. A seat that never reveals is scored as forfeiting the whole escrow — so every client must reveal before requesting adjudication.
  3. MsgAdjudicateSession Runs the engine and pays out. Either party may send it any time; after the dispute deadline anyone may (permissionless crank, so a lost-connection pair cannot lock escrow forever). With no evidence at all the chain refuses to adjudicate until the deadline, after which it becomes a plain refund.

Every submission path must read back its DeliverTx and know what a rejection means: sync-broadcast code 0 only covers CheckTx. The failure taxonomy lives in x/pokerchain/types/tx_failure.go with mirrored copies in C++ (chain_tx_outcome.hpp) and TypeScript (@bitpoker/poker-session/tx-failure). Read the code together with its codespace — pokerchain's code 11 is not the SDK's out-of-gas.

Governance parameters

Bounds are governance-controlled (x/pokerchain/types/params.go). Current defaults:

result_timeout_blocks20 — how long a single submitted result waits for the peer's matching result.
dispute_timeout_blocks1440 (~2 h at 5 s blocks) — after which anyone may crank adjudication. It used to be 50 blocks, which was not a window but a formality: a loser forced a dispute 25 blocks after the winner had submitted and gone away for the evening.
dispute_response_blocks720 (~1 h) — the ADR-010 evidence/secret response window.
dispute_refund_timeout_blocks14400 (~20 h) past the dispute deadline — the final no-engine exit. Mandatory: disabling it would make permanently-locked escrow a valid configuration again.
session_active_timeout_blocks10000 (~14 h) — backstop for sessions that never play.
intent_timeout_blocks720 (~1 h) — how long a pending intent stays matchable.
dispute_fee_bps500 (5%) — the ADR-004 fee charged to the at-fault side only. The honest note in the ADR: the number has no quantitative justification; it is governance awaiting data.
relay_fee_flat / _bps / _cap0 — ceilings on relay self-quoted pricing (ADR-007 P3), not the price itself.
relay_min_bond100 000 000 uchip (100 CHIP) — the Sybil price of a relay identity.
relay_claim_window_blocks / relay_answer_timeout_blocks0 (off) — the endpoint-answer window arithmetic of ADR-007 P1.
intent_congestion_*0 — ADR-012's congestion deposit ships off until governance opts in.

Changing a binary is not upgrading the chain. State migrations only run when a governance-planned, registered upgrade handler reaches its height. Swapping a binary in place gives you new code reading old state with no symptoms — derived indexes self-heal lazily, but params do not. On poker-milestone2-test this killed the entire dispute path (dispute_refund_timeout_blocks stuck at 0 while markSessionDisputed is the only entry to DISPUTED). After any upgrade, check /cosmos/upgrade/v1beta1/module_versions — the version string alone will not show it.

The gas table: one source of truth

How much gas a chain message costs has exactly one source: x/pokerchain/types/gas_bounds.go, pinned by keeper/gas_bounds_test.go which runs every message through the most expensive state it can encounter. Every client's numbers are generated from it (tools/gen-gas-table.py → chain_gas_bounds.generated.hpp and gas-bounds.generated.ts ×2; relayd is in the same Go module and calls types.GasBoundFor directly).

The interesting entry is evidence: a single shuffle message is ~16 KB of stack plus NIZK proof, so MsgSubmitSessionEvidence is 400 000 + 60 × payload_bytes — the only message whose cost is dominated by its own payload. And MsgAdjudicateSession now budgets the engine's own work from the counters the engine returns (signature_verifications, shuffle_proofs_verified) — before that, session 101 died at 1 603 147 gas against a 500 000 bound.

Never hand-write a gas constant. Five uncoordinated copies of one number once left a session's escrow locked for tens of thousands of blocks (ADR-008).
