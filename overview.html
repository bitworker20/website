Internal engineering reference

How BitPoker actually works.

A two-player poker system in which no server ever holds the deck, no operator ever holds the money, and no human referee ever decides a disputed hand. This site is the working description of that system for the people who build and run it. Where this page and the code disagree, the code is right — and the page should be fixed.

The claim

Three powers, three separate answers

Online poker asks players to trust a house with three separate powers: the power to shuffle, the power to see, and the power to pay. Historically all three have been abused, and in a client–server design the first is unauditable by construction — the player receives cards and a promise. BitPoker answers each with a different mechanism, on a different plane.

The shuffle — cryptography

The deck is a vector of elliptic-curve points on FourQ, encrypted under a key neither player holds alone. Each player shuffles once — a secret permutation plus re-encryption — and proves with a Neff-style NIZK that the output really is a permutation-and-re-encryption of the input. For the deck to be biased, someone would have to break the proof system.

The money — the chain

Both stakes are escrowed by pokerchain (Cosmos SDK) at matchmaking time. The happy path releases on a cooperative settlement both players sign. Every state that can hold escrow has a bounded exit — an invariant the test suite walks the state enum to enforce.

The verdict — recomputation

When cooperation fails there is no arbiter. A deterministic C++ engine, linked into every validator via cgo, replays the hand from the players' own signed message history and their revealed session secrets. The verdict is a pure function of on-chain state, bit-identical on every machine and every architecture.

The hard parts were not the parts that look hard. Barnett–Smart and the shuffle proof are textbook. What took real engineering was guaranteeing bit-identical execution of a poker rules engine inside consensus across CPU architectures; discovering that a relay-mediated connection gives no signal at all when the peer dies; and resisting the temptation to fix client problems by adding rules to consensus. Those stories are on the Lessons page, because they should shape every future change here.

Architecture

Four planes, four different trust profiles

Gameplay traffic never touches the chain. The chain never sees a card before a dispute. The relay sees frames and nothing else. Each plane is sized to what it actually needs to be trusted with.

The structural decision

Partitioned by who links it, not by topic

The C++ codebase (~51k lines, with ~39k lines of Go on the chain side) is split along consumer boundaries. This is the single most consequential structural decision in the project, because it is what makes the consensus-critical path defensible against a well-meaning contributor.

bitpoker_gamecore Cryptographic primitives, card/stack types, and the sans-IO subset of each game (*_hand_core, *_rank, *_state, *_protocol). Zero boost::asio, zero wallet code, zero I/O.
bitpoker_core Links gamecore and adds the asio coroutine session layer (common/), Cosmos signing (wallet/), chain and relay clients, and the *_game.* files that are the only ones permitted to touch asio.
poker_adjudicator The C ABI shared by Go validators. Links bitpoker_gamecore only — deliberately not bitpoker_core. A non-deterministic dependency cannot leak into the consensus path by adding a single #include, because the link fails.

The placement rule is mechanical: if grep -l boost/asio matches, the file belongs to the transport layer; otherwise to the core. test/check_gamecore_boundary.cmake enforces it.

Reading order

If you are joining now

  1. 01

    Read the claim, then the threat model

    This page, then the whitepaper's §1.3. Everything downstream is a response to "who might be lying, and what would it cost them".

  2. 02

    Follow one hand end to end

    Protocol → chain → adjudication. A hand that settles cooperatively touches two transactions; a hand that ends in a dispute touches six. Know both paths before touching code.

  3. 03

    Read the Lessons page before your first PR

    Most of the rules in this codebase — "read back every DeliverTx", "every state has a bounded exit", "never fix a client problem in consensus" — are scar tissue, and knowing the scar stops you re-inflicting it.

  4. 04

    Run the interop e2e

    bitpoker/test/interop/run_interop_e2e.sh plays three hands between a WASM peer and a native peer. It is the fastest way to see the whole stack move, and the only way to catch a rules fork between client classes.
