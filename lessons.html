The part that was actually hard

Scar tissue.

The Barnett–Smart construction and the shuffle proof are textbook. What took real work is everything below — failures that were invisible to unit tests, found only by end-to-end runs against real networks, real gas limits and real CLI tools. Each one is written here as symptom → strategy → the rule it left behind, because most rules in this codebase are scar tissue and knowing the scar stops you re-inflicting it.

1. Sessions that could never end

Symptom. A live test run left three matched sessions parked in ACTIVE forever, escrow locked. ClaimSessionTimeout only accepted RESULT_PENDING; becoming ACTIVE set no deadline at all. If both clients crashed, never started, or simply walked away, nothing on chain could ever move that session.

Strategy. Treat "every state has a bounded exit" as an invariant to be audited per state, not an emergent property. session_active_timeout_blocks and the unanswered-assignment void path close the two known dead ends, and escrow_liveness_test.go walks the state enum so a new state without an exit test fails the build.

The rule: in an escrow system, read the state diagram as a liveness diagram. A state with no outgoing timed edge is a fund-loss bug even if no code path is wrong.

2. The disconnect that never disconnects

Symptom. The single most damaging bug found. A player's peer process was killed mid-shuffle; the survivor hung for over ten minutes with no reconnect, no evidence submission, nothing. The reason is structural: the client's WebSocket connects to the relay, not to the peer. When the peer's process dies, that connection stays perfectly healthy — the relay answers pings normally. The transport's idle timeout covers connection idleness, not "connection fine, peer has stopped talking." The design document's assumption that resync relies on the transport read timeout to establish that the peer never returned was simply false under relay transport: that timeout did not exist.

The dispute pathway was, in other words, unreachable. Everything downstream — adjudication, dispute fees, forfeit verdicts — had been unit-tested against a gate no live game could ever open.

Strategy. readPeerMessageBounded caps the wait on the peer specifically, using a budget derived as 2 × action_timeout + 30 (default 150 s). Timeout is handled on the same path as a read failure: reconnect → resync → escalate on chain. The resync handshake read is bounded too, or the handshake hangs the same way.

The budget's derivation matters more than its value. It must be substantially larger than the opponent's own action timeout — otherwise a slow but honest opponent gets classified as absent and a real-money game is escalated into a dispute. Falsely escalating an honest game is worse than waiting longer, so the parameter is derived from the action timeout rather than set independently, making it impossible to configure the two into contradiction.

Result: ten-plus minutes of hanging became 60 s detection → reconnect → bounded resync → on-chain escalation.

3. Empty evidence, and the temptation to fix it on chain

Symptom. When the peer vanishes very early — before the survivor has recorded any message at all — the survivor's history is empty. The chain rejects empty evidence, the follow-up secret is rejected too ("secrets are only accepted for a disputed session"), and the session sits in ACTIVE until the ~14 h backstop.

The tempting fix, and why it was rejected. Relaxing the on-chain gate to accept "connection lost" evidence with no history would let either party pull a live session into DISPUTED with a content-free submission. Empty history is not "undecidable" to the engine — it is a valid verdict, REFUND_UNDEALT, which refunds each side's on-chain opening chips. Since sessions are multi-hand and the chain records the opening stacks, a player several hands down could submit empty evidence, immediately adjudicate, and erase their losses. Plugging that would require further consensus rules — two interlocking rules in consensus for a situation the client can avoid entirely.

Strategy. Fix it in the client, leave the consensus gate intact. If collectMessageHistory() is empty, the client submits neither evidence nor secret — the latter especially, since that transaction is certain to be rejected while still publicly burning the session identity — and marks the session abandonedBeforePlay(). The session runner then drives the pre-existing retreat path (split-pot abort result → result timeout → DISPUTED → reveal → adjudicate), reaching a refund in about six minutes instead of fourteen hours, using only existing primitives and zero consensus changes.

Placing this in the shared session runner rather than in each UI was equally deliberate: unattended clients (the dispatcher worker) have nobody to press a "retreat" button, and they are precisely the ones most likely to face an opponent who never arrives.

The rule: resist fixing client problems by adding rules to consensus. A client-side fix using existing primitives is cheaper, reversible, and doesn't need a network upgrade.

4. Waiting for an opponent who may legitimately be slow

Symptom. If the peer dies before sending its session hello, the survivor blocks forever in initSession — worse than §2, since it never even reaches "session failed."

Strategy, with an explicit trade-off. The §2 budget was not reused, because waiting for a hello is also a legitimate recovery state: the protocol supports both parties re-announcing to resume a session, and a player may return much later. A flat 150 s would break "keep the table open while my opponent reconnects." So the bound is long and configurable — peerHelloTimeoutSeconds, default 1800 s, 0 meaning wait forever — with a per-second countdown surfaced through the event sink to every front end (Qt, mobile, TUI render it; the CLI prints at 30 s intervals and every second for the last ten, because per-second terminal output is noise). On expiry the client does not retry the relay — that only re-spends the same budget — but reuses the §3 conclusion: no messages means no dispute, so go straight to the refund path. Verified live end to end with the bound lowered to 60 s.

5. Transactions that "succeeded"

Three independent failure modes, all of which made the client believe it had reached the chain when it had not:

  • Gas that does not scale with payload. Evidence carries an entire hand's message history; a single shuffle message is ~16 KB. One real hand needed 732 070 gas against a fixed 300 000 shared by all game transactions — meaning every real evidence submission was guaranteed to fail, and to fail after CheckTx passed, so the client saw success. Fixed by scaling: 400 000 + 60 × payload_bytes.
  • pokerchaind tx exits 0 on rejection. The CLI returns success even when the node rejects the transaction, so code 32 (sequence mismatch) and code 11 (out of gas) were both read as success. The submitter now parses the response code, and retries sequence mismatches with a bounded wait of 6 s — longer than one 5 s block, because 2 s never once worked.
  • Broadcast accepted ≠ executed. Acceptance into the mempool says nothing about inclusion or execution. The submitter now polls query tx <hash> for inclusion and code == 0. This immediately surfaced two previously invisible classes of failure: transactions silently dropped from the mempool (how the secret submissions were being lost) and transactions included but failing execution (the out-of-gas evidence).

The rule: treat every layer boundary as an adversary that lies about success — exit codes, mempool acceptance, and CheckTx are all not proof of execution. Confirm at the layer that actually matters, and size resources from payload rather than from a constant.

6. Silent capability gaps between client classes

Symptom. Relay rewards depended on every client class implementing one optional thing: signing a reward receipt. Clients that delegate signing to an external CLI keep the key in a keyring, outside the process, and so silently never sent one; the browser clients never implemented sending at all. Either way the relay waited forever for a second signature, its fee became unpayable to anyone, and nothing anywhere said so.

The same class of bug appeared again on the retreat path: it had only ever supported native signing, so clients that sign via the external pokerchaind CLI — which hold a key name and a keyring, not an unlocked keystore — failed every recovery transaction with native signing requires an unlocked keystore. The visible "retreat" button in the UI had never worked for that entire class of client. Only running the path for real revealed it.

The rule: when a capability is optional per client class, its absence must be reported, not skipped. A silently-skipped feature is indistinguishable from a broken one and costs far more to diagnose. The durable fix for the receipt case was to stop requiring the capability at all, by paying from a fact the chain already had — see settlement as the receipt.

7. Tooling that lies

  • cgo stale archives. Go's build cache does not hash C++ archive contents, so validators kept linking a stale adjudicator. A deliberate ArchiveHash ldflags cache-buster forces relinking, and make adjudicator-check verifies the engine and the .a digest agree.
  • A CLI descriptor that panicked every subcommand. autocli permits exactly one optional positional argument, and it must be last; adding three made pokerchaind panic on every subcommand including init — while go test ./... stayed entirely green. Fixed by moving to flags, plus a root-command guard test verified to catch the regression.
  • A rake charged on refunds. REFUND verdicts were still taking a relay fee while three other void paths were not — the same user-visible outcome was charged or not purely by which code path reached it. Fees are now taken only when the hand truly produced a result.

Each of these was found by end-to-end runs, not unit tests. The standing conclusion: three green unit suites prove three components work in isolation and say very little about the seam between them.

8. Making disputes reproducible at all

Symptom. The dispute end-to-end scenario could not be tested, because a scripted hand runs from shuffle to settlement in about 200 ms — there is no wall-clock window in which to kill a peer. Attempts at 12 s, 4 s, 3 s and 1.2 s all landed after cooperative settlement.

Strategy: deterministic fault injection at protocol granularity, not wall-clock. BITPOKER_FAULT_DROP_AFTER_FRAMES=n makes a client _Exit immediately before emitting frame n, so failures can be placed at exact protocol positions (frame 1 = announce, 2 = session hello, 3 = the first gameplay frame; hence n=3 is "handshake complete, nothing shuffled"). Combined with seat lookup — seats are assigned pseudo-randomly on chain, so injecting into "the second client" hits the wrong seat roughly half the time — this made the entire dispute pathway reproducible on demand.

The rule: failure modes deserve at least as much design as the happy path — and they must be reproducible on demand, or they will only be discovered by users, with money on the table.

Open problems

Stated plainly, because a reference that only lists strengths is marketing.

Unilateral disputes without peer awareness open

A player may, mid-game, submit their genuine history as evidence, pull the session into DISPUTED, and reveal their own secret. An opponent not watching the chain will be judged to have forfeited for failing to reveal, and can lose the entire escrow. The intended fix — clients polling their own session status during play and reacting immediately to DISPUTED — is designed but not yet implemented. This is the most significant known gap.

Settlement granularity in progress

The chain records opening stacks and settles a session as a whole; per-hand checkpointing is designed (ADR-010, milestone M3) and partially built. Until it lands completely, "sit down and play N hands" is constrained, and adjudication reasons about a hand within a session rather than a running stack.

Bad-signature violations are not a verdict open

A history containing a non-participant's signature fails preflight as MALFORMED_REQUEST rather than producing a VIOLATION_BAD_SIGNATURE verdict, because the on-chain model has no "accuser" field. Tampering currently causes failure, not attributable loss.

Collusive "friendly" disputes open

Two colluding players can both decline to submit, producing a BOTH refund and avoiding all fees. Whether this warrants economic suppression is undecided.

The dispute fee is unmodelled open

The default dispute_fee_bps has no quantitative justification (§7.4 of the whitepaper). It is governance awaiting data.

Timeout policy is implicit open

When a hand times out mid-street but both players reveal, the engine decrypts the full board and runs a complete 7-choose-5 showdown — "running it out" for cards never dealt in play. This is a fairness-relevant policy choice currently documented only in implementation comments; it deserves its own ADR.

Browser TLS open

Self-signed certificates with on-chain pinning work only for native clients. Any relay serving browsers needs a real CA certificate; ACME automation is designed but not implemented.

Volumetric DDoS open

Endpoint privacy raises the cost of discovery; it does not address L3/L4 capacity attacks, whose only real answer is network-layer budget.

Relay griefing open

A player who abandons a session mid-hand costs the relay the fee for work it already did, because payment is tied to settlement. The relay loses one flat fee and can deprioritise that player; there is no on-chain consequence for the abandoner beyond the dispute path they invoked.
